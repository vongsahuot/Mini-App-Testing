Credentials and tokens

Customer session MB App ↔ bank

  • Issued by the bank when the customer signs in to MB App.
  • Sent on every customer-side API (C1); the bank takes the customer from it.
  • The partner never receives it.

authCode sign-in handoff

  • Issued by Mini App Service only when consent is current and the customer is registered.
  • One use, valid 60 s, bound to customer + appId.
  • Reaches the partner side by JS callback, SDK callback or verified return link.
  • App-to-App: bound to the partner app's state and code challenge, so a forged or intercepted link is useless.
  • Only the partner server can exchange it (C6); customer data comes back server-to-server.
  • Not used in API linkage: the bank calls the partner with the partnerUserId.

Partner session partner's own

  • Created by the partner server after the authCode exchange.
  • Kept as an HttpOnly cookie (WebView), in SDK memory (SDK) or in app secure storage (App-to-App).
  • The bank never sees or checks it.

mTLS + IP allowlist partner ↔ bank

  • Partner → bank: only from registered server IPs and with the partner's certificate for its clientId.
  • Bank → partner: only to URLs registered at onboarding, with the bank's client certificate.

ES256 request signature partner ↔ bank

  • Every partner ↔ bank API call is signed with ES256 (ECDSA P-256).
  • A timestamp and a nonce are signed with the body, so a captured call cannot be replayed.
  • Each side verifies with the other's public key.

HMAC order checksum order integrity

  • The partner server sets the price and seals the order with an HMAC over a fixed canonical string.
  • Covers appId, orderId, amount, currency, partnerUserId and expiry.
  • Mini App Service verifies it with that partner's key before saving the txn PENDING.

PIN / OTP payment approval

  • Entered only on native MB App screens.
  • An OTP is bound to the paymentRef and amount.
  • Wrong entries can be retried; the customer is locked after N tries.

paymentRef and payLink App-to-App

  • A reference only: it proves nothing about who is paying.
  • MB App signs the customer in first, then loads the payment from the bank's records.
  • Paid only if the txn is PENDING, unexpired and bound to that customer.

Key rules
  • Only enabled Mini Apps the customer is eligible for, and this MB App version supports, are listed and opened.
  • Customer data reaches the partner only after consent to the current consentVersion, and only the consented data scope.
  • The page gets an authCode only by calling login() on the bridge (one use, 60 s); customer data reaches the partner server only server-to-server in exchange for it.
  • The SDK gets an authCode only by calling login() on the host API (one use, 60 s); customer data reaches the partner server only server-to-server in exchange for it.
  • The partner app gets an authCode (one use, 60 s) only in answer to a link request it started itself: it accepts the return only if the state is its own, and the code can be exchanged only with the matching codeVerifier plus the partner's mTLS certificate and signature.
  • The link that opens the partner app from MB App never carries a code or customer data.
  • The page never calls Mini App Service directly; every call goes through MB App or the partner server.
  • The SDK never calls Mini App Service directly; every call goes through the MB App host API or the partner server.
  • The partner app never calls Mini App Service directly; every call goes through MB App or the partner server.
  • There is no authCode and no partner session on the device: the bank calls the partner server-to-server with the partnerUserId.
  • MB App calls only bank APIs. Mini App Service calls only the partner operations registered at onboarding and checks every response against the agreed schema.
  • Integration types in scope: Link WebView (partner hosting), API linkage, SDK embedding, App-to-App. Zip bundle (bank-hosted frontend) is not used.
  • The JS bridge answers only the main frame of the Mini App's allowedOrigins; any other site opens in the system browser without it.
  • The host API (login, openPayment, close) is given only to the SDK instance MB App started. Every SDK version is reviewed, pinned in the MB App release and can be switched off remotely (kill switch).
  • The SDK talks only to its registered hosts (TLS pinning), asks for no extra device permissions, loads no remote code and cannot read MB App storage or screens.
  • Apps hand over only through verified HTTPS links (iOS universal links / Android app links) registered at onboarding, never custom URL schemes.
  • A link carries only a state, a code challenge, a one-time authCode or a paymentRef, never an amount, account or customer data.
  • MB App signs the customer in before showing a payment from a link, and shows it only if the txn is bound to that customer.
  • openPayment uses the appId of the Mini App MB App opened, never one from the page.
  • openPayment uses the appId of the Mini App MB App opened, never one from the SDK.
  • Partner content is data, never HTML or script; MB App renders it in the bank's own native screens.
  • There is no device callback to the partner; it trusts the signed notification (retry topics, then dead-letter) or the status inquiry.
  • The bank calls partners only at URLs registered at onboarding (egress allowlist); partners call the bank only from registered server IPs and with their mTLS certificate.
  • Every partner ↔ bank API call is signed with ES256 (ECDSA P-256) plus timestamp and nonce; each side verifies with the other's public key.
  • Bank staff reach Mini App Admin only with their Active Directory account (admin or normal user).
  • PIN / OTP is entered only in native MB App screens, never in a partner page, SDK screen or partner app.
  • The partner server sets the price and currency and seals the order with an HMAC over a fixed canonical string.
  • MB App shows merchant and amount from the server, never from the page, SDK or link.
  • PENDING → INITIATED → PROCESSING → SUCCESS / FAILED; PENDING / INITIATED → EXPIRED. Every change is a conditional update, so PROCESSING is set once.
  • A txn is never set FAILED by guessing; a timeout stays PROCESSING until Local Gateway confirms, and NOT_FOUND counts only after a confirmed void.
  • Save the final status and an outbox row in one DB transaction; the outbox relay publishes.
  • Refunds are idempotent by refundId and never exceed the amount left to refund.
  • A daily settlement file reconciles every payment and refund: the last safety net. Missing items are flagged, never auto-failed.
  • The JS callback is a UI hint; the partner trusts the signed notification (retry topics, then dead-letter) or the status inquiry.
  • The SDK callback is a UI hint; the partner trusts the signed notification (retry topics, then dead-letter) or the status inquiry.
  • The return link is a UI hint; the partner trusts the signed notification (retry topics, then dead-letter) or the status inquiry.
